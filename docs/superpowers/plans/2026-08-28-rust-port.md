# cort Rust 移植計畫(2026-08-28)

> 決策:全套移植到 Rust——程式與測試都是,TDD,以 Grok 多代理工作流分工。
> 本檔是多代理的共享契約;各 job 不得偏離,有衝突回報協調者(Claude 主線)。

## 0. 不變的鐵律

- ast-grep 釘死 `0.45.2`,經 `Command` spawn 呼叫,版本不符即 fail-closed。
- 不做 in-process parser,不呼叫 `sg` 別名。
- schema v2 相容;既有 v1 DB 開啟後自動遷移。
- `json` / `lean` 輸出形狀必須與現行 JS 版逐欄位一致(render 測試即規格)。
- JS 樹在 cutover 前凍結為參照:任何 job 不得修改 `src/*.js`、`bin/cort.js`、`tests/*.test.js`。
  (僅本計畫與 spec 文件、以及 `rust/` 內的檔案可寫。)
- 使用者 gate 每個 commit;job 只留 working tree,不 commit。

## 1. 佈局

- 新 crate:`rust/`(package 名 `cort`,bin 名 `cort`)。cutover 由 install.sh 改接,JS 於驗收後由使用者決定刪除。
- 依賴白名單:`rusqlite`(bundled,含 FTS5)、`clap`、`serde`/`serde_json`、`sha2`。不引入 YAML parser——pack 規則(.yml)由 ast-grep 自己讀,cort 只做枚舉與 hash。
- toolchain:stable 1.95.0(本機已備)。

## 3. TDD 規則(每個 write job 一體適用)

1. 先寫失敗的 Rust 測試(行為對照 spec 的 176 條表),看它紅,再實作轉綠。
2. 測試不 mock SQLite——用暫存目錄開真 DB;ast-grep bridge 用 tests 既有 fake-ast-grep fixture 的同等物。
3. `cargo test` 全綠且 `cargo clippy` 無 error 才算 job 完成;完成時回報:新增檔案、測試數、與 spec 條號的對照。

## 5. 效度審查修正(Codex adversarial-review,2026-08-28,verdict: needs-attention)

Codex 對 working tree 實作的效度審查提出四個發現,逐條對 code 屬實。**併入本計畫成為對應 job 的需求**:

1. **[high → C3] Cache hit 不省 context token。** `renderRead` 不論 `source` 都逐字輸出內容;SQLite 快取只省磁碟 I/O,量測目標(218 次重讀 ≈124k tool-return tokens)一個都省不到。
   - C3 移植 readings 時,**快取命中預設只回短 receipt**(file、行號範圍、source=store、read_count、內容 hash 前綴),`--content full` 才重送內容;lean 與 json 都遵循。
   - 遺留的開放決策(不擋移植):harness 層的 Read 重讀抑制不歸 cort 管,待使用者另行拍板。
2. **[high → C3] 不得以 size+mtime 作為正確性依據。** 等長修改且 mtime 未變會回傳過期程式碼,違反「stale text is never returned」。
   - 回傳持久化內容前必須驗證 SHA-256;mtime/size 只可作為「需要重驗」的觸發,不可作為「內容未變」的證明。
   - 必備回歸測試:等長修改 + 恢復原 mtime,不得吐舊內容。
3. **[medium → C3] recall 的淘汰只准兩種理由。** ENOENT,或成功讀檔且 hash 確定不符。EMFILE/EIO/暫時性錯誤必須保留筆記、回報 validation_error,不得刪除。
4. **[medium → D + pack 規則] Rust 符號必須帶 owner。** 裸 `function_item`+$NAME 使 `new`/`run`/`from` 互相碰撞,且無法查 `Type::method`。
   - `rust.yml` 補 owner 捕捉(impl/trait 容器),chunk 的 symbol 顯示為 `Type::method`;context 支援 `Type::method` 查詢,先消歧、後套 limit。
   - 必備測試:同名 impl 超過五個、trait 預設方法、`Type::method` 端對端查詢。

**E(驗收)追加**:真實場域量測——finance-cli 的 main.rs 以 `context --content full -f lean` 取單一函式,與整檔 Read 的 token 數做前後對照;receipt 模式下重讀的 tool-return 對照。Codex 原文四發現全錄於 session 紀錄, 此處為需求化版本。

## 10. 使用狀況記錄(Codex 審查後定稿,2026-08-29)

原設計的最大缺陷經 Codex 審出:**command_log 不可放專案 DB**——跨專案聚合、delete 語意、
未索引場景全部衝突。定稿:

- **獨立中央 `$CORT_CACHE_DIR/usage.db`** + 自有 `usage_schema.sql`;專案 `SCHEMA_VERSION` 不動。
- 表:`command_log(id PK, ts UTC ms, project_id NULL, command, args_summary, status,
  error_code, read_source, requested_content_mode, effective_content_mode,
  receipt_hit NULL, index_stale NULL, bytes_out>=0, saved_bytes>=0)`;NULL=未評估;
  索引 `ts`、`(project_id, ts)`。
- `record_command()`:回 `()`、零 panic、零 retry、busy 即棄(≤25ms);絕不碰專案 DB;
  失敗吸收,報表標 `best_effort=true`。
- bytes 語意:`bytes_out`=最終 rendered stdout 的 UTF-8 bytes(含錯誤回應);
  `saved_bytes`=僅 store receipt 命中時「未送出的原始 body bytes」,其他一律 0;
  報表稱 raw body bytes omitted,不得稱總輸出節省。
- receipt 命中率分母只計成功的 auto read(explicit full/receipt 不入),防 flag 污染。
- 保留 90 天:查詢永帶 `ts >= cutoff`;prune 每日至多一次、分批、獨立於 insert;
  `days` 嚴格整數 1..=90(上限=保留期,不用 partial 欄位)。
- `cort usage` 先唯讀聚合輸出,再記自己(本次報表不含本次)。
- `status` 唯讀化:未索引 cwd 不得建立專案 DB(現況 `cmd_status` 先 `open_project`,已證實)。
- 隱私:`args_summary` 僅允許 symbol/專案相對路徑/行號;context 任意 query、recall query、
  struct pattern、clap error message 一律不記;路徑正規化 project-relative。
- help 所有拼法維持零副作用。
- TDD 必備測試:儲存/副作用、recorder 隔離(busy/read-only/corrupt/full)、
  保留期與 days 邊界、bytes 精確值(多位元/escape)、receipt 分母、
  stale 三態(NULL/false/true)、隱私 sentinel、`_global`/`_unknown` 分佈、golden json+lean。
